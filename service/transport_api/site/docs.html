Rate Limit

There is no fixed limit per client. The service is shared by thousands of applications, so please cache what you can: the timetable changes twice a week, real-time data every 30 seconds. An application that asks the same question every few seconds will be throttled.

API Resources

The Transport API builds on REST style resources which respond in JSON. Individual resources are detailed below. Cross Origin Resource Sharing (CORS) is enabled, so you can easily use the API on transport.opendata.ch from any website (avoid setting custom headers though).

/locations

Returns the matching locations for the given parameters. Either query or ( x and y ) are required.

The locations in the response are scored to determine which is the most exact location.

This method can return a refine response, what means that the request has to be redone.

Resource URL

http://transport.opendata.ch/v1/locations

Request Parameters

Name Required Description Example
query optional Specifies the location name to search for Basel
x optional Latitude 47.476001
y optional Longitude 8.306130
type optional Only with query parameter. Specifies the location type, possible types are:
  • all (default): stations and stops first, then addresses and points of interest
  • station: Looks up for stations (train station, bus station)
  • poi: Looks up for points of interest (Clock tower, China garden)
  • address: Looks up for an address (Zurich Bahnhofstrasse 33)
Addresses and points of interest have no id; they can be given as from or to of a connection. 		address

Response parameters

Name Description
stations A list of locations

Example Request

GET http://transport.opendata.ch/v1/locations?query=Basel

Example response

{
    "stations": [
        {
            "id": "8500010",
            "name": "Basel SBB",
            "score": null,
            "coordinate": {
                "type": "WGS84",
                "x": 47.547408,
                "y": 7.589547
            },
            "distance": null
        }
    ]
}

/stationboard

Returns the next connections leaving from a specific location.

Resource URL

http://transport.opendata.ch/v1/stationboard

Request Parameters

Name Required Description Example
station required Specifies the location of which a stationboard should be returned Aarau
id optional The id of the station whose stationboard should be returned.
Alternative to the station parameter; one of these two is required.
If both an id and a station are specified the id has precedence. 		8503059 (for Zurich Stadelhofen)
limit optional Number of departing connections to return.
This is not a hard limit - if multiple connections leave at the same time it'll return any connections that leave at the same time as the last connection within the limit.
For example: limit=4 will return connections leaving at :

  • 19:32
  • 19:32
  • 19:35

datetime optional Date and time of departing connections, in the format YYYY-MM-DD hh:mm. 2012-03-25 17:30
type optional departure (default) or arrival arrival

Response parameters

/fare

What a connection costs: the price of a point-to-point ticket (Streckenbillett) for one adult, full and with a half-fare travelcard, in both classes. Send one connection exactly as /connections returned it; the price comes from the national fare service (NOVA) on opentransportdata.swiss.

Resource URL

POST http://transport.opendata.ch/v1/fare

Request body

One connection object as JSON, with its sections. Walks cost nothing and are left out; each ride needs its stations, times, category and operator, as /connections gives them.

Example request

curl -X POST http://transport.opendata.ch/v1/fare \
     -H 'Content-Type: application/json' \
     -d "$(curl -s 'http://transport.opendata.ch/v1/connections?from=Bern&to=Basel&limit=1' | jq '.connections[0]')"

Example response

{
    "currency": "CHF",
    "product": "Streckenbillett",
    "fares": {
        "2nd": {"full": 42.0, "halfFare": 21.0},
        "1st": {"full": 72.0, "halfFare": 36.0}
    }
}

A price is kept for a week per route - the same stations, categories and operators, at any time of day - and asked again after the timetable change in December. The fare service allows this API a limited number of requests: when they are spent for the minute or the day, /fare answers 503; try again later or show the connection without a price. 400 means a connection that cannot be priced (only walks, an operator the fare service does not know), 404 one the fare service has no price for. Saver tickets, regional passes and children's fares are not covered.

You can limit the response data with the fields parameter. If any fields[] is passed, only the specified fields are in the response. The API is aware of the hierarchy, if you set a field, everything below is in the response unless a more specific (further down in the hierarchy) field is set.

Open Journey Planner (OJP 2.0)

Besides the JSON API above, the same timetable and journey planner answer at /ojp20 - outside /v1, at the path the national planner uses - in the Open Journey Planner 2.0 standard (OJP, CEN/TS 17118): the XML interface of the national journey planner, so that an application written for it can use this API by changing the address. No key is needed.

Resource URL

POST http://transport.opendata.ch/ojp20

Supported requests

  • OJPTripRequest: connections between stops, addresses or coordinates.
  • OJPStopEventRequest: departures or arrivals at a stop.
  • OJPTripInfoRequest: all calls of one journey, by the JourneyRef and OperatingDayRef of an earlier answer.
  • OJPLocationInformationRequest: stops by name, by id or within a rectangle.

Fare, refinement and other requests are not supported. Send the request with Content-Type: text/xml; the namespace prefixes are free (siri: and ojp: as you like).

Stop ids

Stops are named as by the national planner: a station by its SLOID (ch:1:sloid:7000), a platform by its own (ch:1:sloid:7000:4:8). In requests the DiDok number (8507000) works as well. An operating day is written 2026-11-20.

Example request

<OJP xmlns="http://www.vdv.de/ojp" xmlns:siri="http://www.siri.org.uk/siri" version="2.0">
  <OJPRequest><siri:ServiceRequest>
    <siri:RequestTimestamp>2026-11-20T07:00:00Z</siri:RequestTimestamp>
    <siri:RequestorRef>my-app</siri:RequestorRef>
    <OJPTripRequest>
      <siri:RequestTimestamp>2026-11-20T07:00:00Z</siri:RequestTimestamp>
      <Origin><PlaceRef><StopPlaceRef>ch:1:sloid:7000</StopPlaceRef><Name><Text>Bern</Text></Name></PlaceRef>
        <DepArrTime>2026-11-20T07:30:00Z</DepArrTime></Origin>
      <Destination><PlaceRef><StopPlaceRef>ch:1:sloid:3000</StopPlaceRef><Name><Text>Zürich HB</Text></Name></PlaceRef></Destination>
      <Params><NumberOfResults>4</NumberOfResults></Params>
    </OJPTripRequest>
  </siri:ServiceRequest></OJPRequest>
</OJP>

What the answers contain

Valid OJP 2.0, with platforms, real-time times, the line (PublicCode), its category (ProductCategory, Mode/ShortName), the train number and, for trains, the expected occupancy at each departure (ExpectedDepartureOccupancy). A trip of this interface can be priced by the national fare service (OJPFare) as it stands. Different from the national planner: LineRef, JourneyRef and OperatorRef are this planner's own; disruption messages (situations), service attributes and CO2 figures are not given. Connections are the same planner's as in /connections.

Errors are plain text: 400 for a request this interface does not take, 429 when the planner is busy, 502 when it fails.

Source

The API keeps its own copy of the Swiss public transport data and answers every request from it.

Timetable

  • What we fetch: the national timetable of all Swiss public transport as GTFS from opentransportdata.swiss, one file per timetable year (about 300 MB): timetable 2026, timetable 2027.
  • At the source: a complete new version about twice a week, usually on Wednesday and Saturday. The next timetable year is published in the autumn, ahead of the change in mid-December.
  • What we do with it: every hour we look whether a new version is out. A new version is downloaded once, and loaded when the real-time feed has switched to it - the afternoon after publication - so that delays always match the timetable. We keep the days from a week ago to three months ahead in a database; across the December change, both timetable years are merged.
  • In the API: a new timetable answers /locations, /stationboard and /connections within the hour it is loaded; the days held move on weekly.

Real time

  • What we fetch: delays, cancellations and added trips as GTFS-RT from opentransportdata.swiss (an API key is needed).
  • At the source: renewed every 30 seconds.
  • What we do with it: station boards read it every 30 seconds, the journey planner every minute.
  • In the API: delay and prognosis are at most about a minute behind the source.

Connections

  • How: computed here by MOTIS, an open-source journey planner (MIT licence), on the very file of timetable days the database holds and on the same real-time feed, read every minute. For a journey it finds the connections that are best in arrival time and in the number of changes, and /connections writes them in the form /v1 has always used: sections, products, platforms, delays.
  • Changes and walks: transfer times are those of the national timetable, per station; where the timetable gives a walk to a neighbouring stop that is shorter than the station's transfer time, the walk counts, as in the official journey planners. Walks between stops the timetable does not link, and the way from an address or a coordinate to the first stop and from the last stop to the destination, follow the streets of OpenStreetMap - up to 20 minutes on foot. The way to the first stop and from the last is walked at 1.4 m/s (about 5 km/h) to the platform itself, so near a large station it can take a few minutes more than to the station's entrance.
  • In the API: each new timetable and each weekly move of the days held rebuilds the planner, which takes 10 to 20 minutes. It is built beside the running one, which keeps answering until the new one takes over within seconds.

Streets, addresses and places

  • What we fetch: the Swiss extract of OpenStreetMap by Geofabrik (about 550 MB).
  • At the source: edited continuously, the extract published daily.
  • What we do with it: walks to, from and between stops follow its streets, and its addresses and points of interest are what /locations finds besides stops. Searched on this server; no query leaves it.
  • In the API: renewed monthly.

Shared mobility

  • What we fetch: bikes, scooters and cars to rent, as GBFS from sharedmobility.ch of the Swiss Federal Office of Energy (open use, source to be named).
  • At the source and here: every minute. /connections with sharedMobility=1 and the journey planner page use them for the way to the first stop and from the last; without the parameter, /connections walks, as it always has.

Occupancy

  • What we fetch: the occupancy forecast of the railways from opentransportdata.swiss: how full each train is expected to be when it leaves each station, in both classes. It covers trains of SBB, BLS, SOB, Thurbo and zb.
  • At the source: published once a night, for three months ahead.
  • What we do with it: fetched twice a day; the coming week is loaded.
  • In the API: capacity1st and capacity2nd of stops, journeys and connections, and ExpectedDepartureOccupancy in /ojp20.

Fares

  • What we ask: the national fare service (NOVA, OJPFare, beta) on opentransportdata.swiss, for /fare. It is sent the stations, times, categories and operators of the connection - nothing about who asks.
  • In the API: a price is kept a week per route and renewed with the December timetable.

Operator names

  • What we fetch: the names operators go by in the national timetable's HAFAS data (HRDF), from opentransportdata.swiss.
  • In the API: operator gives these shortened names, not the full company names.

The source code is on GitLab. If you show the data, please name its source: Timetable data: opentransportdata.swiss.

History

  • 2012: Opendata.ch starts the Transport API, written by Fabian Vogler (GitHub, his commits on GitLab) and the community, on top of the SBB's timetable interface.
  • 2017: the SBB systems behind it are to be switched off. search.ch steps in with its own web service, and from 31 July 2017 the API translates its answers.
  • 5 October 2026: the national timetable and its real-time data are open data, so the API answers from them directly: its own copy of the timetable and its own journey planner. The parameters and the answers of /v1 stay as they were.
  • November 2026: capacity1st and capacity2nd carry the railways' occupancy forecast, /fare prices a connection, and /ojp20 answers in the Open Journey Planner 2.0 standard.
